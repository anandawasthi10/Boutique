# Feature Ticket List: Handmade Accessories Store

Oct 12, 2026 · @anvi

## How to use this list

These are the frontend tickets for Member A, in build order, followed by a summary of what Members B and C must deliver. Each ticket is one Antigravity task. Tickets with the same prefix and a lower number are built first, and a ticket may not start until the tickets it depends on are done.

**Documents Antigravity must read before any ticket:** the Product Requirements Document, the Technical Architecture Document, the Security and Access Document and the Frontend Specification Document. If a ticket needs something those documents do not state, Antigravity stops and reports the gap instead of guessing.

**Rules that apply to every ticket:**

1. Inspect the existing repository and the files named in the ticket before changing anything. Do not assume a file, dependency or component exists.
2. Change only the files the ticket needs. Do not reformat, rename or refactor unrelated code.
3. Use design tokens from the Frontend Specification. No raw colours, no invented fonts.
4. All data comes through `lib/api/`. No product, price or option data in components.
5. Handle loading, empty, error and success states for every data-driven view.
6. Meet the accessibility baseline in the Frontend Specification.
7. Work at 360 px width and upward, with no sideways scrolling.
8. Write or update tests for the behaviour in the acceptance criteria, then run lint, type checks and the tests.
9. Finish with a completion report: files changed, what was built, how each acceptance criterion was verified, tests run and their results, anything left undone, and any missing contract fields or assumptions.

**Priority labels:** Must-have for launch, Should-have, Nice-to-have. Priorities mirror the Product Requirements Document.

## Group 1: Foundation

### FE-01 Project scaffold

**Priority:** Must-have. **Depends on:** the repository location and package manager being decided.

**Description:** Create the Next.js project with TypeScript and Tailwind using the framework's own generator, in the agreed folder. Add the folder structure from the Technical Architecture Document, an `.env.example` listing the variables for the frontend, lint and format setup, and a test runner. Record every installed version in `/docs/stack-versions.md`.

**Acceptance criteria:**

- The project installs, builds and runs locally with one documented command each.
- TypeScript strict mode is on.
- The folders in the architecture document exist, with a short README or placeholder where empty.
- `.env.example` lists `NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_USE_MOCK_API` and `NEXT_PUBLIC_SITE_URL` with empty values.
- `/docs/stack-versions.md` lists the real installed versions, not guessed ones.
- Lint, type check and the test runner all run successfully.

### FE-02 Design tokens and fonts

**Priority:** Must-have. **Depends on:** FE-01.

**Description:** Implement the colour, typography, spacing, radius and shadow tokens from the Frontend Specification as CSS variables mapped into the Tailwind theme. Load the three proposed fonts with fallbacks. Add the global base styles (background, text colour, focus ring, reduced-motion handling).

**Acceptance criteria:**

- Every colour token in the specification exists with the stated hex.
- Tailwind classes exist for the colours, type scale, spacing and radii.
- Fonts load without layout shift, and fallbacks apply if they fail.
- Focus ring is visible on every interactive element by default.
- A reduced-motion setting disables non-essential motion globally.
- A contrast check of each text and background pair is included in the report, with any failures listed.

### FE-03 Base UI components

**Priority:** Must-have. **Depends on:** FE-02.

**Description:** Build the base components in `components/ui/`: button (primary, secondary, text, icon), text input with label and error, select, checkbox, radio, toast, skeleton, badge, empty state, error state, drawer and modal.

**Acceptance criteria:**

- Each component implements the states in the component styles section.
- Inputs have visible labels, linked error messages and 16 px text.
- Drawer and modal trap focus, close on Escape and return focus when closed.
- Components are keyboard operable and have accessible names.
- Component tests cover the main states of the button, input and drawer.

### FE-04 Component preview page

**Priority:** Should-have. **Depends on:** FE-03.

**Description:** Create an internal page that shows every base component in every state, so the team can review the design system. It must be excluded from production builds or hidden behind a development-only check.

**Acceptance criteria:**

- Every component from FE-03 appears in all its states.
- The page is not reachable in a production build.
- No part of the page is linked from the public navigation.

## Group 2: Data layer

### FE-05 API types

**Priority:** Must-have. **Depends on:** FE-01 and a reviewed API contract (even a draft).

**Description:** Define TypeScript types in `lib/types/` for every object in the Response shapes section of the Frontend Specification: product, option group, option, price quote, cart, cart item, address, order, user and error.

**Acceptance criteria:**

- Each object in the specification has a type with the listed fields, with optional fields marked optional.
- Option group type is a fixed set of the four display types.
- No `any` type is used for API data.
- A short note in the report lists every field name that is still unconfirmed with Member B.

### FE-06 API client

**Priority:** Must-have. **Depends on:** FE-05.

**Description:** Build a small API client in `lib/api/` with one module per area (products, categories, cart, auth, addresses, checkout, orders), each function typed to the contract paths. The client reads the base URL from the public environment variable, converts failures into the single error shape, and is the only place that calls the network.

**Acceptance criteria:**

- Each endpoint in the API spec has a typed function.
- Network failures, non-success responses and malformed responses all become the standard error shape.
- The client sends credentials in the way chosen for authentication from one single configuration point.
- No component imports the network functions directly except through the area modules.
- Tests cover success, field errors and network failure for at least the product and cart modules.

### FE-07 Mock adapter

**Priority:** Must-have. **Depends on:** FE-06.

**Description:** Create an isolated mock implementation of the API client in `lib/api/mock/` with 3 or 4 clearly marked placeholder products covering different option structures (for example fabric and size only; fabric, size and zipper colour; fabric and closure; a product with a toggle). The mock includes a quote function, a cart that stays in memory and a few sample orders. Placeholder images are plain and labelled as placeholders. A single environment flag switches between the mock and the real client.

**Acceptance criteria:**

- With the flag on, every page can load data without a backend.
- With the flag off, the real client is used and no mock code runs.
- The mock returns every error type at least once, selectable for testing (for example a product that fails to load).
- No component, page or test outside `lib/api/mock/` imports mock data directly.
- Deleting `lib/api/mock/` and the flag leaves the project compiling, apart from the one switching file, which is named in the report.
- No Pinterest, Shein or AI moodboard photographs are used as placeholder images.

**Priority:** Must-have. **Depends on:** FE-03, FE-05.

**Acceptance criteria:**

- The card shows only data from the API product summary. No price is calculated in the component.
- The card is a single link with an accessible name containing the product name and price.
- A missing image shows a neutral placeholder block, not a broken image.
- The hover change has a keyboard focus equivalent and respects reduced motion.
- Skeleton, empty and error variants exist.

### FE-12 Shop All and category pages

**Priority:** Must-have. **Depends on:** FE-11, FE-07.

**Description:** Build the Shop All page and the category page, each with a heading, product grid, paging or a load-more control as the API supports, and breadcrumbs. Page state (category, page, sort) lives in the address so pages can be shared and the back button works.

**Acceptance criteria:**

- Loads products and categories only through the API layer.
- Loading, empty and error states behave as in the Security and Access Document.
- An unknown category shows the friendly not-found page.
- The page title and heading reflect the category.
- Browser back and forward restore the previous list state.

### FE-13 Search and filters

**Priority:** Must-have for search by name and category; Should-have for fabric and price filters. **Depends on:** FE-12.

**Description:** Add a search box and a filter and sort control. Filters offered must come from what the API supports. On mobile, filters open in a drawer. Search text is debounced, and the current filters are shown as removable chips.

**Acceptance criteria:**

- Search and filters change the address and the product list.
- A filter the API does not support is not shown.
- The no-results state offers to clear filters.
- Filters are fully operable by keyboard and announced to screen readers.
- Rapid typing does not trigger a request for every keystroke.

## Group 5: Product page and configurator

### FE-14 Product gallery

**Priority:** Must-have. **Depends on:** FE-03, FE-05.

**Description:** Build the gallery with one large main image and a thumbnail row. Clicking or tapping a thumbnail changes the main image. On mobile the main image can be swiped.

**Acceptance criteria:**

- Images and alt text come from the API product.
- A product with one image shows no thumbnail row; a product with none shows a neutral placeholder.
- Thumbnails are buttons with accessible names and a clear selected state.
- The first image loads with priority; the others load lazily.
- The image change respects reduced motion.

### FE-15 Product detail page shell

**Priority:** Must-have. **Depends on:** FE-14, FE-07.

**Description:** Build the product page at the product's address: breadcrumbs, gallery, name, description, starting price and a slot for the configurator. Load the product by its slug.

**Acceptance criteria:**

- Loading, not-found and error states exist and match the Security and Access Document.
- The page title uses the product name.
- The layout stacks on mobile and uses two columns on desktop, with the purchase area staying visible while scrolling on desktop.
- Description text is displayed as plain text.

### FE-16 Option group components

**Priority:** Must-have. **Depends on:** FE-03, FE-05.

**Description:** Build the four option group components (swatch, colour, chips, toggle) and the wrapper that picks one from the group's display type. Each follows the Configurator specification.

**Acceptance criteria:**

- A swatch shows its texture image and the selected fabric's name; a colour dot shows its colour and a name for the selected one.
- Selected is shown by a border and a check icon, not by colour alone.
- Unavailable options are disabled and show their reason.
- Required and optional groups are labelled.
- All four components work by keyboard, with the correct roles (single choice groups behave as a radio group; toggle as a switch).
- A group with an unknown display type does not crash the page; it shows a safe fallback and the report mentions it.

### FE-17 Configurator state and price quotes

**Priority:** Must-have. **Depends on:** FE-16, FE-07.

**Description:** Build `useConfigurator`: it holds the selected option IDs, applies any default options from the API, requests a price quote when the selection changes (debounced, ignoring outdated responses), and exposes whether the selection is complete and valid.

**Acceptance criteria:**

- No selection is made for a group unless the API supplied a default.
- Add to cart is not allowed until every required group has a selection and the latest quote is valid.
- A quote response for an old selection never replaces a newer one.
- Quote failures keep the last valid price marked as outdated and block Add to cart.
- When an option becomes unavailable, its selection is cleared and the customer is told.
- Tests cover required groups, invalid combinations and out-of-order quote responses.

### FE-18 Preview, price breakdown and selection summary

**Priority:** Must-have. **Depends on:** FE-17, FE-14.

**Description:** Build the preview panel (photo, option preview image when available, otherwise the large swatch card), the price breakdown and the selection summary.

**Acceptance criteria:**

- The preview changes only when the API supplies an image for the selection; otherwise the photo stays and the swatch card shows the chosen fabric. No image is recoloured or generated.
- The breakdown lists the base price, each option's change and the total, exactly as returned by the quote.
- Prices are formatted in rupees in the Indian number style.
- The summary lists chosen options and names any required choices still missing.
- Price changes are announced to screen readers.

### FE-19 Add-to-cart bar

**Priority:** Must-have. **Depends on:** FE-17, FE-21 and FE-22. Build FE-21 and FE-22 first, even though they are numbered later.

**Description:** Build the quantity control and the Add to cart button, with disabled, loading, success and error states, and the Buy Now button that adds the item and goes to checkout.

**Acceptance criteria:**

- The button is disabled with a visible reason until the configuration is complete and valid.
- A second click while loading does nothing.
- On success, the cart drawer opens and the cart count updates from the API response.
- On failure, the configuration is kept and a retry is offered.
- The configuration sent contains option IDs only.

### FE-20 Build Your Own entry

**Priority:** Must-have. **Depends on:** FE-15, FE-17.

**Description:** Build the guided entry page: a product picker using products from the API, then the same configurator as the product page. There is no separate configurator.

**Acceptance criteria:**

- The picker shows only products from the API.
- Choosing a product shows the same configurator component used in FE-15 through FE-19.
- Changing the product resets the selections.
- Loading, empty and error states exist.

## Group 6: Cart

Build FE-21 and FE-22 before FE-19 in Group 5.

### FE-21 Cart state

**Priority:** Must-have. **Depends on:** FE-06, FE-07.

**Description:** Build one cart store that loads the cart from the API, exposes add, update quantity, change configuration and remove actions, and updates only from API responses. It also exposes the item count for the header.

**Acceptance criteria:**

- Every change goes through the API layer and the store updates from the returned cart.
- No price, subtotal or total is calculated in the store.
- Pending actions are tracked so buttons can show loading and avoid double submission.
- Failures leave the previous cart in place and expose an error message.
- Tests cover add, update, remove and a failed update.

### FE-22 Cart drawer

**Priority:** Must-have. **Depends on:** FE-21, FE-03.

**Description:** Build the cart drawer, opened from the header cart button and after adding an item. It lists items with image, name, chosen options, quantity and server-calculated line price, with a subtotal and a Checkout button.

**Acceptance criteria:**

- Opens and closes with the focus rules in the component styles section.
- The empty state has a clear link to Shop All.
- Items with a price or availability notice show it clearly, and Checkout is blocked until the notice is acknowledged or the item removed, as the API requires.
- Quantity changes and removal show loading and error states per item.
- The subtotal and total come from the API cart.
- Add-to-cart feedback is visible and respects reduced motion.

### FE-23 Cart page and edit configuration

**Priority:** Must-have. **Depends on:** FE-22, FE-17.

**Description:** Build the full cart page with the same items as the drawer, an order summary, and an Edit configuration action on each item that reopens the configurator pre-filled with the item's selected options. Saving updates the same cart item.

**Acceptance criteria:**

- Edit configuration opens the same configurator component, pre-filled from the cart item.
- If a previously chosen option is no longer available, it is cleared and the customer is told.
- Saving sends the new option IDs to the API and shows the updated price from the response.
- Cancelling changes nothing.
- The page works on mobile and desktop and handles empty, loading and error states.

## Group 8: Addresses and checkout

### FE-28 Saved addresses

**Priority:** Must-have. **Depends on:** FE-27.

**Description:** Build the saved addresses page: a list of address cards with edit, delete and set-as-default actions, and an address form used for adding and editing. Address fields follow the Indian format in the Response shapes section.

**Acceptance criteria:**

- The form validates the required fields, a six-digit PIN code and a phone number format before sending, and shows the server's field errors.
- Delete asks for confirmation and shows loading and error states.
- Setting the default address updates the list from the API response.

- The same form component is used in checkout (FE-29).

### FE-29 Checkout flow

**Priority:** Must-have. **Depends on:** FE-23, FE-28, FE-24.

**Description:** Build the checkout as clear steps: choose or add a delivery address, review the order, then continue to payment. Checkout is for signed-in customers only. A progress indicator shows the current step, and the customer can go back without losing entries.

**Acceptance criteria:**

- A signed-out visitor is sent to login and returns to checkout.
- A saved address can be selected, or a new one added with the shared address form.
- The order review lists items with their options and the totals returned by the API. No total is calculated in the frontend.
- If the API reports a changed price or unavailable item, checkout shows it and does not continue until it is resolved.
- The Pay button shows loading and cannot be double-submitted.
- A failure to start checkout keeps the cart and shows a retry option.
- Keyboard and screen reader use works through every step.

### FE-30 Handoff to payment

**Priority:** Must-have. **Depends on:** FE-29, and the payment gateway and the checkout response shape being agreed with Member B.

**Description:** Implement the frontend half of starting a payment, using only what the checkout response provides. Build it behind a small, replaceable payment module so the gateway can be changed without touching the checkout screens.

**Acceptance criteria:**

- No gateway secret appears in browser code or in the repository.
- Card or UPI details are never entered on this site; only the gateway's own screens collect them.
- When the customer comes back from the gateway, the site shows the payment result screen (FE-31) based on the order status from the API.
- If the contract for this step is not yet agreed, the report states the missing information and a clearly isolated mock is used instead.

## Group 9: Payment states and orders

### FE-31 Payment result screens

**Priority:** Must-have. **Depends on:** FE-30, FE-07.

**Description:** Build the screens for pending, success, failed and cancelled payment. Every screen is driven only by the order's payment status from the API, never by the gateway redirect itself.

**Acceptance criteria:**

- On return from the gateway, the screen fetches the order and shows the state the API reports.
- Pending: a clear waiting message, automatic status checks at intervals for a limited time, then a manual refresh button.
- Success: the order number and a link to the order and to continue shopping.
- Failed: a clear message and a way to retry payment or return to the cart, as the API allows.
- Cancelled: a message that the order was not completed, saying nothing was charged only if the API confirms it.
- An order that does not belong to the customer shows the not-found page.
- Screens work on mobile and are announced to screen readers when the status changes.
- Tests cover all four states with the mock.

### FE-32 Order confirmation

- The page can be reloaded or revisited without creating anything new.

### FE-34 Order details and status

**Acceptance criteria:**
