# Security and Access Document: Handmade Accessories Store

Oct 12, 2026 · @anvi

## 1. Authentication

The brief requires sign up, login and forgot or reset password. The login method and how sessions are kept are for Members B and C to decide. The frontend is written against a small, method-neutral contract, so changing the method later does not mean rewriting screens.

**What the frontend needs from the backend:**

- Create an account.
- Log in and log out.
- Return the current user, or a clear "not signed in" response.
- Start and complete a password reset.
- A consistent error shape for failures (see section 5).

**Method options for B and C to choose from:**

| Option | What the customer does | Notes |
| --- | --- | --- |
| Email and password | Signs up with email and password | Matches the brief's sign up, login and reset screens directly |
| Email and password plus Google sign-in | Chooses either | Adds a provider to set up; needs extra screens and rules |
| One-time code by SMS or email | Enters a code | Needs a message-sending service and has a running cost |

**Working assumption until decided:** email and password, because it fits the screens in the brief.

**Frontend requirements regardless of method:**

- The frontend never stores passwords or reads session secrets.
- Protected pages redirect to login and return the customer afterwards.
- The password reset screen never reveals whether an email address has an account.
- Login and signup forms show clear field errors and a safe, general message for failed logins.

## 2. User roles and permissions

Release 1 has two roles in the app: a guest and a signed-in customer. There is no admin role because there is no admin dashboard; the team changes product data directly in the database, which is outside the app.

| Action | Guest | Signed-in customer |
| --- | --- | --- |
| View homepage, categories, products, About, Contact | Yes | Yes |
| Search, filter and configure a product | Yes | Yes |
| Get a price quote | Yes | Yes |
| Add to cart | Decision open (see section 7) | Yes |
| Create an account, log in, request password reset | Yes | Not needed |
| Checkout and pay | No | Yes |
| Save and choose addresses | No | Yes |
| View My Orders and order details | No | Yes, own orders only |
| View or edit someone else's data | No | No |
| Change product, price or option data | No | No |
| Mark a payment as successful | No | No, only the backend can |

**If an admin role is added later,** it needs its own document section. Nothing in release 1 should assume it exists.

## 3. Data access rules

These are the rules the backend must enforce on every request. The frontend hides what a customer cannot use, but hiding a button is not security. The backend checks every request, whatever the screen shows. Member B enforces these and Member C tests them.

| Data | Who can read | Who can change |
| --- | --- | --- |
| Products, categories, options, images | Everyone | No one through the app |
| User account | The signed-in user, their own only | The same user, their own only |
| Addresses | The signed-in user, their own only | The same user, their own only |
| Cart | The signed-in user, their own only | The same user, their own only |
| Orders and order items | The signed-in user, their own only | Created by checkout; status changes only by the backend |
| Payments | The backend only; customers see payment status on their order | The backend only |

**Rules:**

- The user ID always comes from the signed-in session, never from a value the browser sends.
- Asking for another customer's address or order returns "not found", the same response as for something that does not exist.
- Price, totals and stock status are always calculated on the server. Values sent from the browser are ignored.
- Payment status is set only by the server after the gateway confirms it.

## 4. Frontend security rules

These rules apply to every frontend task.

| Area | Rule |
| --- | --- |
| Secrets | No secret keys, tokens or passwords in browser code or in the repository. Only variables meant to be public may reach the browser. |
| Prices and status | The frontend never trusts a price, total or payment status it computed itself. It displays what the API returns. |
| Payment redirect | Returning from the gateway proves nothing. The result screen fetches the order status from the API before showing success. |
| Input | Forms validate on the client for quick feedback, and also display the server's errors. Client validation is a convenience, not protection. |
| Output | Text from the API (names, descriptions, addresses) is displayed as plain text. No component inserts raw HTML from API data. |
| Redirects | After login, the return address must be a page on this site. Addresses pointing elsewhere are ignored. |
| Links | Links that open other sites open safely, without passing the current page to them. |
| Storage | No passwords, payment details or session secrets in browser storage. Only harmless preferences (such as sound on or off) may be stored. |
| Payment details | Card or UPI details are entered only on the gateway's own screens, never in this site's forms. |
| Errors | Error messages shown to customers are friendly and general. They never include technical details, stack traces or other customers' information. |
| Dependencies | Add a library only when needed, and record it with its reason in the completion report. |
| Logging | No personal data or payment data in console output. |

## 5. Error handling guide

Every failure gets a defined response so the site never fails silently. The wording below is a starting point; final copy follows the brand's tone. Member B's API returns one error shape with a code, a message and optional field errors.

| Failure | What the customer sees | What the site does |
| --- | --- | --- |
| Product list or product fails to load | A short message and a Try again button | Keeps the page layout; retries on request |
| No products match search or filters | "No products found" with a way to clear filters | Shows suggestions or categories |
| Product not found | A friendly not-found page with a link to Shop All |  |
| Selected option no longer available | The option shows as unavailable with a short reason | Clears that selection and asks the customer to choose again |
| Invalid option combination | A short note explaining which choices don't go together | Keeps Add to cart disabled |
| Price quote fails | A note that the price could not be updated | Keeps the last valid price visibly marked as outdated and blocks Add to cart until a quote succeeds |
| Add to cart fails | A message and a Try again button | Keeps the configuration so nothing is lost |
| Cart item price or availability changed | A notice on the item explaining the change | Asks the customer to confirm before checkout |
| Wrong password or unknown email | A general message that email or password is incorrect | Never says which one was wrong |
| Signup email already used | A message suggesting login or reset | Follows the rule the backend agrees on for revealing this |
| Session expired | A message asking the customer to log in again | Returns the customer to where they were after login |
| Form field invalid | A message next to the field | Focus moves to the first invalid field |
| Address service rejects a PIN code or phone number | A message next to that field | Keeps the other entries |
| Checkout fails to start | A message and a Try again button | Does not clear the cart |
| Payment pending | A clear "waiting for confirmation" screen | Checks the order status again at intervals and offers a manual refresh |
| Payment failed | A clear failure message and a way to retry | Keeps the order and cart as the backend states |
| Payment cancelled | A message that nothing was charged, if the backend confirms that | Offers to return to the cart |
| Order not found or not the customer's | A not-found page | Shows no data about whether it exists |
| Network offline or very slow | A message that the connection is unavailable | Shows loading skeletons and retry options |
| Unexpected error | A general apology and a way back to the homepage | Reports the error to monitoring if the team adds it |

## 6. Edge cases to handle before launch

Each item needs a defined behaviour and a test. Member C owns the test list; Member A and B build the handling.

- [ ] A customer submits an empty or half-filled form (login, signup, address).
- [ ] A customer opens a page that needs login while signed out, then logs in and expects to return to it.
- [ ] A customer tries to open another customer's order or address by changing the address in the browser.
- [ ] A product is edited or removed in the database while a customer is configuring it or has it in the cart.
- [ ] A price changes between adding to the cart and paying.
- [ ] A required option is skipped, or a customer reaches Add to cart through the keyboard while it is disabled.
- [ ] A customer double-clicks Add to cart, Place order or Pay.
- [ ] A customer pays and closes the tab before the confirmation screen loads, then returns later.
- [ ] The gateway confirms payment late, or the customer returns before the backend knows the result.
- [ ] The same payment is reported twice.
- [ ] A customer opens the cart in two browser tabs and changes both.
- [ ] A very long name, address or option label breaks a layout.
- [ ] A product has no images, or an image fails to load.
- [ ] A product has option groups the frontend has not seen before (a new group type).
- [ ] The connection is slow or drops in the middle of checkout.
- [ ] A customer uses only a keyboard or a screen reader to configure and buy.
- [ ] A customer has reduced-motion turned on, or has sounds disabled.
- [ ] PIN code or phone number is in the wrong format.
- [ ] The session expires while the customer is on the checkout screen.

## 7. Open decisions

- [ ] **Login method (B and C):** email and password, with or without Google sign-in or one-time codes?
- [ ] **Session approach (B and C):** how sessions are kept, and how long they last.
- [ ] **Guest add to cart (team and client):** can visitors add to the cart without an account, or must they log in first?
- [ ] **Signup with an existing email (B):** does the site say the email is taken, or send a neutral message?
- [ ] **Password rules (B and C):** minimum length and any other requirements.
- [ ] **Rate limits (B):** limits on login, signup, password reset and price quotes.
- [ ] **Payment cancelled (B):** can the backend confirm that nothing was charged, so the screen can say so?
- [ ] **Monitoring (team):** will error monitoring be added before launch?
- [ ] **Data protection (client and team):** what personal data is collected, how long it is kept, and whether a privacy policy and terms pages are needed at launch.
