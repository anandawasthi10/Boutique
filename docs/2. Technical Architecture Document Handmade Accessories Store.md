## 2. How the pieces fit

The browser talks only to the backend API, and only the backend talks to the database and the payment gateway.

| Layer | Responsibility | Owner |
| --- | --- | --- |
| Pages and components | Render what the API returns; collect input; show loading, empty, error and success states | A |
| Frontend API layer | The only place that calls the backend; converts responses into typed objects | A |
| Backend API | Validates options, calculates prices, manages cart, orders and payments | B |
| Database | Stores products, options, users, addresses, carts and orders | C (schema), B (access) |
| Payment gateway | Takes payment and reports the result to the backend | B |

**Path of a typical request (adding a configured product to the cart):**

1. The customer changes an option in the configurator.
2. The frontend asks the API for a price quote for the current selection.
3. The backend checks the selection is valid and returns the price breakdown.
4. The frontend displays that quote. It does not calculate prices itself.
5. The customer clicks Add to cart. The frontend sends the product and the selected option IDs.
6. The backend validates again, stores the cart item and returns the updated cart.
7. The frontend updates the cart drawer from the response.

**Payment status rule:** the frontend never decides that a payment succeeded. After the customer returns from the gateway, the frontend fetches the order's status from the backend and shows what the backend says.

## 3. File and folder structure

This is the proposed layout. When Antigravity scaffolds the project it must keep whatever the Next.js generator creates and add to it, never restructure it. Folders marked B or C are listed so everyone knows where they sit; Antigravity working for Member A must not edit them.

```
project-root/
  app/                      A  Routes and page layouts (App Router)
    (storefront)/           A  Home, shop, category, product, build-your-own, about, contact
    (auth)/                 A  Sign up, login, forgot and reset password
    (account)/              A  Profile, addresses, orders, order detail
    (checkout)/             A  Cart, address, review, payment states, confirmation
    api/                    B  Backend route handlers
  components/
    ui/                     A  Base components: button, input, drawer, toast, skeleton
    layout/                 A  Header, footer, mobile nav, preference controls
    catalogue/              A  Product card, grid, filters, search
    product/                A  Gallery, preview panel, price breakdown
    configurator/           A  Option groups, swatch, chips, colour dots, toggles, summary
    cart/                   A  Cart drawer, cart item, quantity stepper
    checkout/               A  Address list, address form, order summary, status views
    account/                A  Order card, order timeline
  lib/
    api/                    A  Typed API client and one service module per area
      mock/                 A  Temporary mock adapter, isolated and removable
    types/                  A  TypeScript types for API responses
    hooks/                  A  useConfigurator, useCart, motion and sound preferences
    validation/             A  Client-side form rules
    format/                 A  Currency, date and address formatting
    server/                 B  Server-only code (database access, payment, auth)
  prisma/                   C  Schema, migrations, seed script
  public/                   A  Static assets and placeholder images
  styles/                   A  Global styles and design tokens
  tests/                    A, B, C  Test files in subfolders by owner
  docs/                     All  Contract, data dictionary, status glossary, stack versions
```

**Rules:**

- Components never call `fetch` directly. They use the functions in `lib/api/`.
- Mock data lives only in `lib/api/mock/` and is never imported by a component.
- No product, price, fabric or option data is written in a component file.

## 4. Frontend architecture rules

These rules apply to every Antigravity task for Member A.

| Topic | Rule |
| --- | --- |
| API calls | All calls go through `lib/api/`, one module per area (products, cart, auth, addresses, checkout, orders). Components import those functions, never `fetch`. |
| Mock adapter | The mock implements the same functions and types as the real client. A single environment flag switches between them. Removing the mock means deleting one folder and one flag. |
| Types | Every API response has a TypeScript type in `lib/types/`. Types follow the agreed contract; if the contract is missing a field, stop and report it instead of inventing one. |
| Prices | Displayed prices are always values returned by the API. No component adds, multiplies or rounds prices. |
| Option groups | The configurator renders whatever option groups the API returns. No product-specific option lists in the frontend. |
| Data states | Every data-driven view has loading, empty, error and success states. |
| Errors | The API client converts failures into one error shape (code, message, optional field errors) so forms can show messages per field. |
| Auth state | A single provider exposes the current user and login state. Protected pages redirect to login and return the customer afterwards. |
| Cart state | One cart store, updated from API responses, not by guessing locally. |
| Forms | Client-side validation for fast feedback, with the server's field errors displayed when it rejects input. |
| Secrets | Nothing secret in browser code. Only variables intended to be public are exposed. |
| Payment | A gateway redirect is not proof of payment. The result screen fetches the order status from the API. |
| Accessibility | Keyboard operable, visible focus, labelled inputs, sufficient contrast, reduced-motion respected. |
| Motion and sound | Animations lightweight and skippable by preference. Sound is off by default, never plays on page load, and has a mute control. |
| Scope | A task changes only the files it names. Unrelated files are not reformatted or refactored. |

## 5. Proposed database schema

Member C owns the real schema. This is a plain-English starting point so that the API contract and the frontend types can be agreed. Field names and types are for C to finalise; the frontend only depends on what the API returns.

| Table | Purpose | Main fields | Relationships |
| --- | --- | --- | --- |
| Users | Customer accounts | ID, name, email, phone, password credential handled by the auth approach, created date | Has many addresses, carts and orders |
| Addresses | Saved delivery addresses | ID, user, recipient name, phone, address lines, city, state, PIN code, default flag | Belongs to a user |
| Categories | Product groupings | ID, name, slug, description, image, sort order | Has many products |
| Products | A sellable product type | ID, name, slug, description, base price, category, active flag, sort order | Belongs to a category; has many images and option groups |
| Product images | Photos for a product | ID, product, image URL, alt text, sort order | Belongs to a product |
| Option groups | A choice a customer makes for a product (fabric, size, zipper colour, lining, strap, closure) | ID, product, label, display type (swatch, colour, chips or toggle), required flag, sort order | Belongs to a product; has many options |
| Options | One selectable value inside a group | ID, group, label, price change, available flag, swatch image or colour value, optional preview image | Belongs to an option group |
| Option rules | Combinations that are not allowed or that change availability | ID, product, rule description, the options involved | Belongs to a product |
| Carts | A customer's current cart | ID, user, updated date | Belongs to a user; has many cart items |
| Cart items | A configured product in the cart | ID, cart, product, quantity | Has many cart item selections |
| Cart item selections | The options chosen for a cart item | ID, cart item, option group, option | Belongs to a cart item |
| Orders | A placed order | ID, order number, user, address copy, status, payment status, totals, created date | Has many order items and payments |
| Order items | What was bought, as it was at purchase | ID, order, product name, selected options as text, unit price, quantity | Belongs to an order |
| Payments | Payment attempts for an order | ID, order, gateway reference, status, amount, created date | Belongs to an order |

**Design points for C to consider:**

- Order items store the product name, chosen options and price at the time of purchase, so later catalogue changes do not rewrite past orders.
- The delivery address is copied onto the order, so editing a saved address does not alter old orders.
- Order and payment statuses use one agreed list, documented in `/docs/status-glossary.md`.
- Products, option groups and options are entered manually by the team in release 1, so seed data and a simple, repeatable way of entering it matter.

## 6. Environment variables and configuration

Variable names below are proposals. Values are never written in the repository or in these documents.

| Variable | Visible to the browser? | Purpose | Owner |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | Yes | Base URL the frontend uses for API calls | A, with B |
| `NEXT_PUBLIC_USE_MOCK_API` | Yes | Switches the frontend between the mock adapter and the real API | A |
| `NEXT_PUBLIC_SITE_URL` | Yes | Public site address, used for links and redirects | A |
| Database connection string | No | Backend database access | C, B |
| Auth secret or signing key | No | Session or token security | B, C |
| Payment gateway public key | Only if the gateway requires it in the browser | Starting the payment experience | B decides |
| Payment gateway secret and webhook secret | No | Server-side payment and webhook checks | B |
| Email service credentials | No | Order and password-reset emails | B |
| Image storage credentials | No | Uploading product images | C, B |

**Configuration rules:**

- Only variables starting with `NEXT_PUBLIC_` may reach the browser, and nothing secret may use that prefix.
- Commit an `.env.example` listing every variable name with an empty value. Never commit real `.env` files.
- Real values are set separately for development, testing and production.
- The mock flag must default to the real API in production builds.
